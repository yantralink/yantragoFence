# YantraGO — Security and Google Play Readiness Audit

**Audit date:** 29 September 2026. **Source revision:** `56709ca`. **Decision:** NOT READY for a public production release until the critical/high security findings and mandatory Play release gates below are resolved.

## 1. Scope, evidence, and limitations

This is a source/configuration security assessment and Google Play readiness review, not a penetration-test certificate or a guarantee of Play approval. Reviewed areas: Spring authentication, JWT/refresh lifecycle, REST authorization and customer ownership, STOMP/WebSocket access, command dispatch boundaries, TCP device admission, selected infrastructure/CI configuration, Next.js authentication/dependencies, Flutter storage/logging/maps/push/logout, Android manifest/signing, and relevant architecture documents. Business endpoints and dependencies were sampled; this is not a claim that every file or possible vulnerability was exhaustively checked.

No production logins, device commands, network attacks, database changes, credential use, deployments, or Play Console submissions were performed. Application code was not changed. Findings distinguish source-confirmed defects from risks requiring runtime or operational confirmation. File paths below are relative to the repository root; line numbers refer to the audited revision. Secret values are intentionally not reproduced.

## 2. Security findings and required remediation

Severity reflects impact and prerequisites, not just scanner labels. **P0:** immediate containment/critical fix. **P1:** fix before public release. **P2:** hardening; document any temporary acceptance, owner, and expiry. Source-confirmed means the code behavior was traced, not that production exploitation was attempted.

### SEC-01 — Shared customer password and credentials in release notes — Critical / P0
- **Evidence:** `backend/src/main/java/com/yantrago/api/service/CustomerService.java:26–37,102–110` assigns the same fixed password to each new customer. `.github/workflows/build-apk.yml:89–117` includes privileged/customer default login information in generated non-draft release notes pointed at the production domain. Publication history, repository visibility, and current server credential validity were not inspected.
- **Impact/action:** Anyone who knows a customer's phone/login identifier and the default can potentially take over that account. Remove the shared-password onboarding path; use expiring, single-use verified invitations/activation and user-chosen credentials. No ordinary session or command permission before activation. Inventory affected accounts internally, rotate/invalidate affected credentials and sessions, and require secure activation/reset. Privileged accounts need MFA or equivalent approved step-up protection.
- **Containment:** Restrict affected access and stop publishing credential-bearing release text. Owners must separately approve changes to published releases/history and production account revocation. Treat removing text as cleanup, not credential rotation; preserve incident evidence safely. Never paste credentials into this report, logs, or issue trackers. **Prompt:** Phase A.

### SEC-02 — Customer-level object authorization missing on physical commands and data — Critical / P0
- **Evidence:** `database/migrations/V18__add_customer_role.sql:16–30` grants customers command-write and machine/location/telemetry read permissions. `CommandController.java:37–40` permits command-write; `service/CommandService.java:73–95` checks only organization membership, not customer assignment. `service/MachineService.java:93–147` omits assignment checks for customer-filtered lists/status/latest telemetry, and `getMachine` uses `ifPresent`, failing open if the customer record is absent. `service/LocationService.java:90–131` checks only the organization. These Java paths are under `backend/src/main/java/com/yantrago/api/`.
- **Impact/action:** A customer with another machine UUID in the same organization can reach commands and sensitive machine data outside their assignment. This is distinct from cross-organization isolation and especially serious for energized fencing equipment. Implement a shared machine-access policy covering organization, explicit role/permission, active customer linkage, and current assignment; apply it to commands, histories, analytics, alerts, locations, telemetry, settings, geofences, exports, and realtime destinations as applicable. Customer-provided filters cannot widen scope. A missing/inactive customer link must deny access.
- **Acceptance:** Two customers in one organization plus a second organization; unauthorized reads return the chosen consistent 403/404, unauthorized commands create no command/attempt/message, valid owner/admin paths still work. Include deleted/unassigned/reassigned machines and absent customer records. **Prompt:** Phase B.

### SEC-03 — Cross-tenant WebSocket subscriptions lack resource authorization — High / P1
- **Evidence:** `backend/src/main/java/com/yantrago/api/websocket/StompChannelInterceptor.java:56–88` accepts arbitrary `/queue/` and structurally valid `/topic/.../...` subscriptions for any session containing a user ID. It never looks up machine/device ownership or permissions. `TrackingWebSocketController.java:41–58` merely logs the application's subscribe message; direct STOMP SUBSCRIBE does not depend on that method. `config/WebSocketConfig.java:56–83` wires this interceptor and the shared broker.
- **Impact/action:** An authenticated socket can subscribe to another customer's/tenant's known machine topic. UUID secrecy is not authorization. Deny by default; permit exact destinations, validate UUIDs, enforce the same machine policy as REST, reject raw broker queues/wildcards, and bind private user queues to the authenticated principal. Server-side expiry/revocation must close existing subscriptions, not only reject new frames. **Prompt:** Phase C.

### SEC-04 — Deactivation, locking, password change, and tenant changes do not invalidate sessions — High / P1
- **Evidence:** `backend/src/main/java/com/yantrago/api/service/AuthService.java:149–204` refreshes after loading a user without checking active/locked/organization-active state, and uses the stored refresh token's organization rather than validating current membership. `security/JwtAuthFilter.java:53–96` trusts JWT claims without a session/account-state check. `service/UserService.java:136–181` changes password/status without session revocation; customer lifecycle code similarly deactivates users without revocation.
- **Impact/action:** Disabled or locked users can keep refreshing; old permissions/tenant context can survive changes. Introduce an authoritative account/session version or equivalent bounded revocation mechanism, revoke refresh families on security changes, validate current user/organization on refresh, and apply revocation to REST and active sockets. Define logout-one versus logout-all behavior. Require token purpose, issuer/audience, distinct access/refresh keys, and explicit validation where appropriate. **Prompt:** Phase D.

### SEC-05 — Refresh replay revocation can roll back; rotation is not atomic — High / P1
- **Evidence:** `backend/src/main/java/com/yantrago/api/service/AuthService.java:149–202`: a `@Transactional` refresh method revokes all user tokens then throws `IllegalStateException` on replay. Default Spring rollback semantics roll back the revocation with the exception. `repository/RefreshTokenRepository.java:13–19` performs an unlocked lookup; no atomic consumed-state update is shown. Concurrent refreshes can both observe an unused token.
- **Action/acceptance:** Ensure security revocation commits independently of the rejected refresh, and atomically consume each refresh token once using locking or a conditional update. Design family/session semantics deliberately. Prove committed revocation and concurrent one-time use with real PostgreSQL transaction integration tests, not Mockito-only tests; test replay, rollback, logout, expiration, and concurrent client refresh. **Prompt:** Phase D.

### SEC-06 — Rate limiter trusts spoofable forwarding headers and runs before authentication — High / P1
- **Evidence:** `backend/src/main/java/com/yantrago/api/security/RateLimitFilter.java:42–87` uses unbounded maps, trusts the first `X-Forwarded-For` value, and exempts loopback strings. `config/SecurityConfig.java:66–68` places the rate filter before JWT authentication. `infra/vultr/nginx/nginx.conf:60–67` appends rather than replaces incoming forwarding values. Nginx separately has a 10-request/second limiter, so this is not a claim that all protection is absent.
- **Action/acceptance:** Resolve clients only through explicitly trusted proxies; overwrite untrusted forwarding headers at the first edge. Split unauthenticated/IP/login-account limiting from post-authentication user/tenant/command limits; use bounded expiring state and shared counters for multiple instances. Add backoff without easy account-lockout abuse, consistent 429/Retry-After responses, and uniform login failures. Test the real security chain, header spoofing, loopback via proxy, distributed attempts, and bounded bucket growth. **Prompt:** Phase E.

### SEC-07 — Missing tenant context is treated as platform administrator — High-risk design / P1
- **Evidence:** `backend/src/main/java/com/yantrago/api/security/TenantGuard.java:32–57` bypasses organization checks when context is null; `service/OwnerContextService.java:34–39` defines super-admin as null context. `security/TenantContextFilter.java:37–53` does not assert that only an authenticated SUPER_ADMIN may lack an organization.
- **Scope/action:** An unsigned/invalid JWT does not automatically gain access: signature authentication still exists. The defect is a fail-open privilege convention if a signed non-admin token lacks the claim or context propagation fails. Require explicit authenticated platform authority for bypass; distinguish absent context from approved platform context; keep queue consumers on explicit device-derived tenant context. Test missing/malformed context and anonymous/non-admin/admin combinations. **Prompt:** Phase B.

### SEC-08 — Mobile response logging exposes authentication and personal data — High / P1
- **Evidence:** `mobile/lib/core/network/api_client.dart:23–33` installs an unconditional Dio logger with response bodies enabled and `print`. `mobile/lib/core/auth/auth_service.dart:22–27` sends login through that client and receives both tokens in the response.
- **Action/acceptance:** Remove sensitive payload logging in all builds, not just header logging; debug instrumentation must be explicitly enabled and redacted. Never log tokens, passwords, personal coordinates, customer data, or push tokens. Test login/refresh/error logs with sentinel values, inspect release-device logs, and retain only safe correlation/status/timing metadata. Log access on ordinary Android is restricted, but diagnostic collection, debugging, and compromised devices remain exposure paths. **Prompt:** Phase F.

### SEC-09 — Reusable bearer tokens appear in WebSocket URLs — High / P1
- **Evidence:** `backend/src/main/java/com/yantrago/api/websocket/WebSocketAuthInterceptor.java:49–81` accepts query tokens; `mobile/lib/features/commands/providers/command_socket_provider.dart:79–87` puts the access token in the URL. The shared socket pattern is also used by other realtime features. URLs may enter proxy/diagnostic logs; deployed log formats were not inspected.
- **Action/acceptance:** Use Authorization headers for native clients and an approved browser-compatible flow such as a short-lived, one-use socket ticket bound to the session, or properly secured STOMP CONNECT authentication. Make HTTP upgrade and STOMP authentication agree; do not simply make all `/ws` traffic public. Redact query strings at the edge, avoid URL-token logging, and test expired tickets, reuse, origin checks, account switches, and session expiry. **Prompt:** Phase C.

### SEC-10 — TCP login identity is not authenticated; connection replacement is unsafe — High / P1
- **Evidence:** `device-gateway/src/main/java/com/yantrago/gateway/tcp/fencing/FencingProtocolHandler.java:154–167` accepts a parsed IMEI and records a session. `tcp/fencing/FencingTcpServer.java:152–160` registers it for command routing. `tcp/DeviceConnectionRegistry.java:25–38` overwrites an IMEI connection and lets an older disconnect remove the newer mapping. `service/DeviceAuthService.java:36–47` only checks IMEI existence, not active status, and the inspected login path does not call it. These latter paths are relative to the gateway Java package.
- **Action/acceptance:** Add active-device admission and current-session ownership outside reused parser logic; make replacement/removal conditional on the same connection identity. IMEI allowlisting is necessary but is not cryptographic authentication. Establish hardware capabilities with the vendor: authenticated transport where supported, or private APN/VPN/network isolation and documented residual risk for legacy devices. CRC/checksum is not authentication. Test unknown/inactive/duplicate identities, stale disconnects, and ACK attribution in an isolated simulator, never against energized equipment. **Prompt:** Phase G.

### SEC-11 — TCP connection resource exhaustion — High / P1
- **Evidence:** `device-gateway/src/main/java/com/yantrago/gateway/tcp/fencing/FencingTcpServer.java:39–40,81–90,109–123` allocates an unbounded cached thread pool and continues after read timeouts indefinitely, including before successful admission. Concox/JT808 server files also use cached thread pools.
- **Action/acceptance:** Bound connections/workers and admission rates, enforce pre-authentication deadlines and maximum idle lifetime, and apply gateway/edge backpressure and per-source quotas compatible with carrier NAT. Preserve legitimate heartbeat behavior and protocol framing. Test idle/pre-login exhaustion and recovery with controlled local load. **Prompt:** Phase G.

### SEC-12 — Vulnerable web dependencies and incomplete CI security gates — High / P1; scanner includes Critical
- **Evidence:** `admin-web/package.json:12–24` pins Next.js 14.2.5; the audit found affected `next` and nested `postcss`. Representative advisory: [GHSA-f82v-jwr5-mffw](https://github.com/advisories/GHSA-f82v-jwr5-mffw), middleware authorization bypass. Applicability depends on actual features/deployment; this report does not claim middleware bypass is proven on this app. `.github/workflows/security-scan.yml:9–15,27–35,61–67` misses root Gradle/mobile/lockfile-only PR triggers, uses `trivy-action@master`, and does not explicitly fail on vulnerability severity. `.github/workflows/build-apk.yml:53–55` ignores analyzer failure in the release workflow, although separate mobile PR CI is blocking.
- **Action/acceptance:** Upgrade to supported patched dependency lines after checking all current advisories and release age; do not assume the audit's suggested 14.2.35 fixes every listed advisory. Produce resolved Java, Node, Dart/native and image SBOMs; scan built artifacts and images; gate releases on analyzed/tested/scanned commits. Pin actions to reviewed immutable revisions, use least-privilege permissions, and expand triggers. Do not use forced audit fixes or weaken security policies. **Prompt:** Phase H.

### SEC-13 — Browser token storage, permissive CORS, and broad public routes — Medium / P2
- **Evidence:** `admin-web/src/lib/api-client.ts:20–51` reads/stores both tokens in localStorage. `backend/src/main/java/com/yantrago/api/config/SecurityConfig.java:56–64,121–132` allows all origin patterns with credentials and publicly permits all auth paths plus Swagger/OpenAPI. `/auth/me` and locale update currently contain manual authentication checks; this is not evidence of anonymous profile access.
- **Action/acceptance:** Prefer short-lived in-memory access tokens and a Secure/HttpOnly/SameSite refresh/session cookie using the existing backend/web deployment, with explicit CSRF protection for cookie-authenticated endpoints. Preserve secure mobile bearer authentication. Allowlist production CORS origins, review CSP/security headers, permit only intentional public routes, and restrict documentation/management exposure by environment. CORS alone does not let a malicious site read a bearer token from another origin's localStorage. **Prompt:** Phase I.

### SEC-14 — Security audit interceptor does not persist audit records — Medium / P2
- **Evidence:** `backend/src/main/java/com/yantrago/api/security/AuditLogInterceptor.java:14–18,52–58` logs to SLF4J only. The audited source search found no write-path invocation of the existing `AuditLogService` from this interceptor. Machine command/attempt records DO exist; this finding concerns authentication/administrative security audit coverage, not absence of all command auditing.
- **Action/acceptance:** Persist security events with actor, resolved tenant/platform scope, target, outcome, trusted client metadata and correlation ID; no secrets or whole request bodies. Capture deny/failure outcomes as appropriate and use a deliberate transaction strategy so rejected actions do not erase their audit evidence. Restrict audit modification/export, define retention, and verify event durability. **Prompt:** Phase I.

### SEC-15 — Map WebView loads remote executable code and discloses precise coordinates — Medium / P1 privacy review
- **Evidence:** `mobile/lib/features/machines/pages/machine_location_map_page.dart:84–86,151–168` loads unrestricted JavaScript from unpkg with no navigation delegate/CSP shown. `mobile/lib/core/services/reverse_geocoding_service.dart:87–129` sends exact machine coordinates directly to public Nominatim. Its comment mentions one request/second, but only a per-instance cache is implemented; no actual throttle. Tiles reveal the viewed area/IP to OSM. No token bridge or confirmed exploitable input injection was observed in this map.
- **Action/acceptance:** Bundle the reviewed map library, constrain navigation/resources, serialize labels safely, validate coordinates, and preserve attribution. Choose an approved production map/geocoding provider and data-processing terms; use the existing backend for bounded caching/rate control if appropriate. Public Nominatim explicitly restricts heavy use and submission of personal/confidential material [P12]; assess farmer-linked coordinates before transmitting them. Inform users of third-party map/geocoding transfers, and obtain prior affirmative consent when the unexpected-sensitive-data rule applies. **Prompt:** Phase J.

### SEC-16 — Logout failure can leave local credentials intact — Medium / P1
- **Evidence:** `mobile/lib/features/auth/providers/auth_provider.dart:130–145` awaits push cleanup before calling `AuthService.logout`, which contains secure-storage cleanup. `features/push/providers/push_notification_provider.dart:263–283` catches its HTTP error but `FirebaseMessaging.deleteToken()` can still throw. Then the UI is set unauthenticated without necessarily clearing stored auth tokens. The notifier also reads the current user only after replacing authenticated state with loading.
- **Action/acceptance:** Capture identity before state changes; guarantee local credential/cache/socket/pending-navigation cleanup in a top-level finally regardless of push/network errors. Define current-installation versus all-device push logout; prevent stale-account notifications after switching. Test offline logout, Firebase/storage errors, app restart, two accounts on one phone, and multi-device login. Keep server-side revocation work in Phase D. **Prompt:** Phase F.

### SEC-17 — Deployment trust boundaries need tightening and live verification — Medium / P1 deployment gate
- **Evidence:** `infra/docker/docker-compose.staging.yml:16–17,35–36,49–51` publishes database/cache/broker/management ports on unspecified host interfaces. `infra/vultr/firewall/db-server.ufw:13–17` and sibling firewall templates fall back to broad SSH/private-network ranges. Separate setup scripts include plaintext internal service connections. Systemd hardening and HTTPS configuration are present, so deployed exposure/encryption cannot be inferred solely from these templates.
- **Action/acceptance:** Remove unnecessary host port publication or bind loopback/private interfaces explicitly; fail setup if administrator/source addresses are missing; use least-privilege DB/broker users, isolated vhosts and TLS with peer validation for cross-host data paths. Verify real firewall/cloud rules, active Nginx config, log redaction, encrypted backups, retention, restore drills and service-account rotation with the owner. Do not run setup/deploy/seed scripts during the audit. **Prompt:** Phase I.

### SEC-18 — CSV export lacks spreadsheet-formula neutralization — Medium / P2
- **Evidence:** `backend/src/main/java/com/yantrago/api/service/ReportExportService.java:107–131` quotes commas/quotes/newlines but leaves formula-leading text unchanged. Whether a particular exported field is attacker-controlled must be confirmed per report type.
- **Action/acceptance:** Apply a tested spreadsheet-safe string-cell encoder for formula-leading/control-character cases while preserving actual numeric values, valid CSV structure, and UTF-8. Test user-controlled names/text through the real export path. Keep export authorization and range/row/memory limits explicit. **Prompt:** Phase I.

## 4. Detailed, phase-wise implementation prompts

**Use one phase at a time.** Each prompt inherits this instruction: “Read `AGENTS.md` and the relevant architecture/implementation sections first. Preserve the two-service backend + gateway architecture, existing shared RabbitMQ contracts, asynchronous ACK-based command behavior, UUIDs, tenant isolation and RBAC. Use Flyway versioned migrations only; never edit applied migrations. Follow existing Java 17/Spring and Riverpod/Dio conventions, validation, safe errors, SLF4J and tests. Do not change reused Concox/JT808 parsing logic or expose secrets. Obtain explicit approval for production revocation, deletion, destructive DDL, deployment, configuration-policy changes and third-party actions. First write failing regression tests where supported. Implement only this phase, verify it, then STOP and ask the user to verify and authorize the next phase.” The audit itself implements none of these phases. Recommended execution order is **A, B, D, C, E, F, G, H, I, J, K**, so the session-revocation foundation exists before realtime integration. Each phase must be independently testable and deployable; do not mark it complete while a required control depends on unfinished work. If emergency containment needs an earlier operational action, obtain the owner's specific approval instead of silently implementing another phase.

### Phase A — Secure customer activation and incident containment (SEC-01)
**Copy/paste prompt:** “Replace shared customer-password onboarding in CustomerService with production-ready, single-use, expiring activation. Before coding, ask the owner to approve an existing delivery/identity-verification channel and account-recovery policy; do not fabricate an SMS/email provider. Store only activation token hashes, rate-limit activation/resend, avoid account enumeration, and atomically consume activation. ## 5. Practical Play Store publication sequence

1. **Contain security risk first:** resolve P0 findings immediately; complete P1 release gates or obtain an explicit technically justified exception where appropriate. No exception can waive Google policy. Arrange an independent retest of command/customer isolation, sockets, tokens and gateway admission.
2. **Confirm business inputs:** choose the truthful developer account type, legal entity/support contacts, public versus managed-private distribution, target countries/audience, account provisioning/signup/deletion model and monetization. Complete Play identity/organization verification and secure Console access with MFA/least privilege [P9].
3. **Finalize application identity:** confirm `com.yantrago.yantrago`, brand/icon, Firebase app registration and signing-certificate requirements for the services actually used. Establish Play App Signing and protect the separate upload key. Existing debug-signed sideloads cannot normally be updated in place by a differently signed Play build; plan a communicated reinstall/migration without silently deleting local data.
4. **Finish legal/privacy work:** publish the approved HTML privacy page; verify signed-out access and in-app links. Complete the data inventory and deletion-scope decision; supply an external deletion-request resource when required. Reconcile FCM/map SDK behavior with Data safety answers; verify encryption and retention claims [P2–4,P11–12].
5. **Create the app in Play Console:** select default language, app/game, free/paid, countries and category that accurately describe the product. Supply app name, short description (80 characters), full description (up to 4,000), support details, 512×512 icon, 1024×500 feature graphic and at least two compliant screenshots; use synthetic account/location data and localized assets where useful [P10]. State that compatible YantraGO hardware and a provisioned account/connectivity are required; don't imply guaranteed theft prevention or phone tracking.
6. **Complete App content:** Privacy policy, Data safety/deletion, Sign-in details/App access, ads, audience/content rating and all applicable Console declarations. No ads SDK was observed, but owner must verify the final binary before choosing “no ads.” Do not select a human-health use case solely because a screen says battery health. Confirm purchases against Payments policy if monetization changes [P6,P13].
7. **Provide safe reviewer access:** give a stable test login only through Play Console, with realistic synthetic machines, history and notifications. Support every reviewable feature without real equipment hazards or dependence on the owner's phone/OTP. Use the same disclosed app behavior, not a reviewer-detection bypass; isolate the demo tenant from real device routing. Do not publish these credentials in GitHub releases.
8. **Build and inspect the release artifact:** use Phase K. Typical commands, after secure signing setup: `flutter pub get`, `flutter gen-l10n`, `flutter analyze`, `flutter test`, then `flutter build appbundle --release --build-number=<approved-monotonic-number> --dart-define=API_BASE_URL=https://yantrago.com --dart-define=WS_BASE_URL=wss://yantrago.com/ws`. Run from `mobile/`; the expected output is `build/app/outputs/bundle/release/app-release.aab`. These are release instructions, not commands successfully run in this audit.
9. **Validate what will be installed:** use `bundletool validate --bundle=<release.aab>` and `bundletool dump manifest --bundle=<release.aab> --module=base`; inspect target SDK, package/version and permissions. Inspect `bundletool dump config --bundle=<release.aab>` for 16 KB alignment. Verify native ELF segments and run Android build-tools `zipalign -c -P 16 -v 4 <generated.apk>` on generated APKs; ZIP alignment alone is insufficient. On the test device, `adb shell getconf PAGE_SIZE` must return `16384` for the 16 KB test [P5]. Inspect AAB/APK signing with the correct tooling and test Play-generated APKs, not only a locally sideloaded debug build.
10. **Internal testing first:** upload AAB to internal testing, resolve Console errors, review App Bundle Explorer permissions/device support and pre-launch reports. Test cold start, login/reset, role/tenant separation, network loss/reconnect, GPS/maps, notifications in all app states, denied notifications, language/accessibility, account switching/deletion and command ACK/timeout behavior. Real-machine safety tests require separate owner authorization.
11. **Closed testing and production access:** if the account is subject to the new-personal-account rule, maintain at least 12 genuine testers continuously opted in for 14 days and apply for production access with truthful test feedback [P8]. Even when not mandatory, run representative external device testing. Passing the time/tester threshold does not automatically grant production approval.
12. **Submit and operate:** recheck policy status, metadata and release notes, select the available controlled rollout options, and submit for review. First-production rollout options may differ from update staged rollouts. Monitor crashes/ANRs, API failures, denied access, abnormal commands and gateway health; keep a tested stop/rollback procedure. Recheck SDK/policy requirements and Data safety at every release, not only the first upload.
